## 3. 3a4f196b — `--step_rows`

### 3.1 맞는 것
- **행당 1/N**: `backward_scale = chunk_weight × rows_norm`, `chunk_weight = rows_c / pack.rows`(기본·Anima 둘 다), `rows_norm = pack.rows / N` → 모든 청크가 `rows_c / N`, 마지막 짧은 팩(5행 → 0.375·0.25 = 행당 0.125)도. fp64 시뮬레이션(배치 `[3,8,1,2,6,4,5]`, 토큰 예산 3100 으로 `[3,3,2]`·`[3,1,2,2]`… 청크)에서 매 스텝 기울기 == (1/8)Σ grad(loss_i) == accelerate 의 batch 1 × 누적 8 스텝(부분 5행 그룹 포함), SGD 궤적 전체 동일. accelerate 가 `/gradient_accumulation_steps` 하는 것은 `validate_step_rows` 가 1 을 강제해 상쇄. 로그 손실은 팩 행의 소박한 평균, `_step_func_loss_accum` 은 기울기와 같은 스케일.
- **에폭 스텝 수 산술**: `validate_step_rows → dataset_rows_per_epoch → steps_per_epoch` (2736-2738) → `max_train_steps = epochs × packs`(2743) → `set_max_train_steps` → `get_scheduler_fix(num_training_steps = max_train_steps)` 모두 팩 단위; `accelerator.prepare` 뒤 RowPacker 랩(3070) 이후의 모든 `len(train_dataloader)`(3246-3247, 3265-3271 출력, 3292 `ss_num_batches_per_epoch`, 3597/3620-3627 재개 산술, 3946 진행바)가 패커. 공식 자체(`BucketBatchIndex → min(bucket_batch_size, 남은 수)`)는 `BaseDataset.__getitem__` 이 주는 행수와 일치(78행 16배치 → 10팩 실측). **단, 실제 로더가 매 에폭 그 목록을 그대로 내놓지 않는다 — B2.**
- **재개**: `skip_first_packs(initial_step-1)` + 루프의 `continue` 1회 = 정확히 `resumed_step % P` 팩 스킵(accelerate 경로와 같은 형태); `_SkippedPacks.__len__ = packs - k` 는 accelerate `SkipBatchSampler.__len__` 과 같은 의미; `calculate_val_loss` 는 받은 객체의 `len()` 만 읽음. 재개 뒤 데이터 순서는 중단 없는 에폭과 동일(같은 DataLoaderShard 를 처음부터 돎). 기존(업스트림) 사항: 검증을 할지 말지 정하는 바깥 게이트(4246/4262)는 전체 패커 `len` 을 받으므로 재개 에폭에선 에폭 말 검증이 안 뜰 수 있음 — accelerate 경로도 동일 구조, 이 커밋의 회귀 아님.
